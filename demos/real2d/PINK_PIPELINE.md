# Пайплайн розоволосой героини по формулам (`pink_v4`)

Документ фиксирует, **как именно** исполняются формулы из
[FORMULAS.md](pink_v4/FORMULAS.md) в этом репозитории, и что уже измерено.
Ничего здесь не выдаётся за готовый результат: статусы в конце.

## 1. Что показали измерения шитов

Инструмент [tools/inspect_sheet.py](tools/inspect_sheet.py) (по требованию
контракта §4 — факты, а не предположения) дал:

| Факт | Значение |
|---|---|
| Сетка | 12 колонок × 6 рядов, но клетки **не целочисленные** (147.8 / 181.0×120.7 / 128×170.7 / 167.8×130.2) |
| Содержимое | **крупнее клетки**, вылезает в соседей; часть колонок слиплась в одну компоненту |
| Выравнивание слоёв | **отсутствует**: каждый ряд нарисован по центру своей клетки, общей рамки у слоёв нет |
| Alpha | честная (0..255), но под прозрачными texel'ами лежит мусорный RGB |

Вывод, который определяет всю геометрию: **якоря нельзя измерить внутри шита**.
Слой `hair_back` в клетке (1, c) не знает, где находится череп из клетки (0, c).
Значит:

* **геометрия** (12 yaw-якорей: где череп, глаза, плечи, бёдра, колени) берётся
  измерением по **собранным** видам `assets/pink_full_character_target_yaw_pitch_v1.png`.
  Target — reference-only и в runtime не попадает, но как источник авторских
  якорей он и предназначен («сравнивать дизайн, палитру, силуэт; конкретные
  углы верифицировать» — README пакета);
* **appearance** берётся из послойных шитов: для каждого слоя и каждой колонки
  вырезается его фактический габарит ([tools/pink_author.py](tools/pink_author.py),
  разметка по связным компонентам с разрезом слипшихся по границам колонок).

## 2. Какие формулы где исполняются

| Формула | Где | Состояние |
|---|---|---|
| §3 `q(θ,u,s)=μ+B·a(θ,u,s)+δ_sem` | `tools/pink_bake.py` (план) — SVD якорей, `B=V[:,0:r]`, ранг по остаточной ошибке | частично: та же математика уже работает в [tools/bake_real2d.py](tools/bake_real2d.py) для head-only |
| §4 тензор `F_k(θ)·T_l(u)`, `T_{l+1}=2uT_l−T_{l−1}`, K=3, L=2 | bake: базис и частотная регуляризация | K=3/L=0 работает; L=2 требует pitch-якорей, которых в пакете нет → в отчёт как незавершённое |
| §6 softmax `ℓ_j=κ_j(cosΔθ−1)−(u−u_j)²/(2h_j²)+logρ_j` | runtime: веса appearance-якорей | заменяет текущий smoothstep-гейт; регистрация чартов — на bake |
| §7 `α_i=v_i·gate_i·A_i·O_i`, нормализация по owner group | runtime: композиция | нормализация группы лиц уже есть (alpha 1.0 вместо 0.75) |
| §8 barycentric warp, `sign(A)=sign(A0)`, `A/A0≥0.05` | `src/real2d4.c` | работает: top-left, билинейная выборка, hard-validator вывернутых |
| §9 глубина `d_i=Σ c_ikl F_k T_l`, premultiplied over | runtime | **отклонение**: сейчас глубина — авторские константы, а не функция; перевести на фит |
| §11 энергия Baker'а | отчёт bake | считается только `E_anchor`-часть (реконструкция якорей); остальные слагаемые — план |

## 3. Порядок работ

1. Измерить landmarks по 12 собранным видам target'а (череп, глаза, нос, рот,
   плечи, локти, кисти, бёдра, колени, стопы) → `authoring/pink.anchors.json`.
2. Свести якоря и вырезы шитов в патчи с cage/mesh/UV (лист → общая UV-рамка).
3. Фит `μ, B, c` (§3–§4), ранг по остаточной ошибке, отчёт по каждой детали.
4. Разметить видимость/топологию (§7) и softmax-веса (§6) по колонкам.
5. Body/clothing sheets — та же процедура в рамке тела.
6. Bake в `.r2d4`, рендер движком, сравнение с target (contact sheet + IoU силуэта).

## 5. Что уже проверено и что провалилось (важные факты)

**Провал: регистрация слоёв одной лишь энергией изображения.** Инструмент
[tools/pink_register.py](tools/pink_register.py) ищет посадку каждого слоя
жадной минимизацией `E = w_sil(1−IoU) + w_col·|RGB−RGB*|` по собранному
target'у. Формально энергия падает (IoU 0.547 → 0.569), но решение
бессмысленно: `hair_back` уезжает к правому краю кадра и уменьшается, потому
что такая энергия вознаграждает любое покрытие силуэта и не знает, *какая
деталь где должна быть*. Это ровно то, о чём предупреждает §12: сетки,
соответствия и точные авторские anchors — входные данные; одной оптимизацией
их не получить. В §11 для этого и стоит отдельное слагаемое `E_landmark`
(20 из суммы весов) — без размеченных landmarks энергия вырождена.

**Провал: автоматическая разметка клеток листа лица.** Контактный лист всех
клеток ([tools/pink_gridview.py](tools/pink_gridview.py), кадр в
`authoring/preview_pink_face_yaw_layers_v1.png`) показал: клетки ряда содержат
НЕ изолированную деталь, как просил промпт, а сборку из нескольких элементов
(глаз + бровь + линия века в одной клетке), а габариты содержимого выходят за
клетку по вертикали: у клетки глаза bbox = (74,0,181,120) при клетке 181×121,
у рта — тонкая полоса (94,0,161,12) в самом верху клетки. То есть строки листа
лица не находятся в общей рамке лица, и «взять клетку» нельзя ни для геометрии,
ни для UV.

**Следствие для пайплайна:** посадка слоёв задаётся авторскими landmarks
(нормированными по `W_h`/`H_h` головы, §10), а оптимизация допускается только
как локальное уточнение вокруг авторской инициализации с landmark-ограничениями.

**Проверено измерением:** колонки шитов несут поворот в самом artwork (лицо
сужается от фронта к профилю), поэтому межколоночная интерполяция геометрии не
нужна — нужна регистрация слоёв внутри колонки и blend appearance в общей UV (§6).

## 6. Вертикальный срез: pink-ассеты прошли через движок

Собрано: [tools/pink_front_slice.py](tools/pink_front_slice.py) — явная таблица
деталей фронтальной колонки → атлас → `assets/pink_front_v4.r2d4` → кадр
движком. Три бага найдены и исправлены на этом пути:

1. **Вырожденное кольцо.** Патч может принадлежать только одному кольцу
   (§7), поэтому у одиночного патча кольцо из одной записи; формула
   `up*down` давала в anchor-точке 0.5 и кадр выходил полупрозрачным.
   Исправлено в `ring_weight()`: кольцо из одной записи — вес 1.0.
2. **Словарь `owner_group`.** Рантайм знает только `face/eye/eyelid/nose/
   mouth/bangs/hair_back/lock`; незнакомое имя трактуется как 0 — «группа
   лица», которая КОПИТСЯ СУММОЙ. Мои имена (`hair`, `features`) попадали
   туда, пересекающиеся слои складывались аддитивно, и лицо выгорало в белый.
   Плюс `clip_to` работает только со значением `face`, а не `head`.
3. **Единица H у baker'а.** `bake_real2d.py` жёстко брал `UNIT_PX=380` и
   `origin=[256,72]`; теперь читает `placement.head_unit_px/head_top_y` из
   authoring (у розовой единица 240 px).

Кадр движка сейчас: розовый боб, заколка-кошка, красные глаза, светлая кожа —
персонаж узнаваем; чёлка ещё садится на глаза, нос/рот смещены. Это
**промежуточный** результат среза, а не соответствие рефу.

## 7. Все 12 колонок в одном контейнере

Собрано: [tools/pink_all_columns.py](tools/pink_all_columns.py) — таблица деталей
применяется ко всем 12 yaw-колонкам шитов, одна полочная упаковка атласа,
12 колец по 12 записей (fade 15° = половина шага, §18). Контейнер
`assets/pink_v4.r2d4`: 121 патч, 968 треугольников, 12 anchors, dim 605,
rank 1 (все ключи одного патча одинаковы — вариацию несёт artwork колонки,
а не манифолд). Предел патчей рантайма поднят 64 → 256
(`R2D4_MAX_PATCHES`, память ≈512 КБ).

Кадры движком на 8 углах: 15 патчей/120 треуг. в среднем, raster 9–25 мс,
ошибок нет.

**Что видно и что не так:** фронтальные углы (0/30/60/300) узнаваемы —
боб, заколка, глаза; на профильных (90/150/240) пряди и чёлка ложатся
ПОВЕРХ лица, потому что посадка слоёв задана одними и теми же правилами для
всех колонок. Artwork колонки несёт поворот, но взаимное расположение слоёв
обязано меняться по колонке — это следующий шаг (посадка от измеренного
силуэта головы ДАННОЙ колонки, а не от общих констант).

## 8. Ещё два бага весов (найдены замером, не на глаз)

Диагностика через `$.real2d.patchWeights(id, yaw)` — она печатает реальный
gate каждого патча, поэтому видно, что именно рисуется на данном угле.

1. **`fade` трактовался как полуокно.** В `ring_weight` окно перехода было
   `2·fade` вместо `fade`, поэтому в самой anchor-точке `up = smoothstep(0.5)
   = 0.5`: вес не доходил до 1, и на кадре одновременно жили ДВЕ соседние
   колонки — это и давало «многоглазие» и общую бледность. Теперь `fade` —
   полная ширина перехода (§18: 15°), полуокно `fade/2`. Авторинг стадии A
   удвоен, чтобы кадры тёмноволосой головы не поехали.
2. **Пики весов стояли на границах, а не на anchor'ах.** Запись кольца
   активна на дуге `[a, b)`, поэтому границы обязаны быть серединами между
   ключами: `a_k = key_k − fade/2`. После правки на каждом anchor-угле
   активны ровно 12 патчей (одна колонка) с gate 1.0, а на середине между
   ключами — по 0.5 у двух соседних колонок, то есть partition-of-unity
   (§7) выполняется.

## 9. Видимость §7 и измеренная регистрация волос

**Поле `visibility` в контейнере.** Патч может нести окно видимости
`{center_deg, half_deg, fade_deg}`: `v = 1 − smoothstep((|Δ| − half)/fade)`.
Авторинг задаёт окна для головы (центр 0, half 95, fade 25), носа (80/25),
рта (85/25), чёлки (90/30) и черт лица (центр = φ детали, half 70, fade 25).
Проверено замером на `patchWeights`: yaw 0 → 14 патчей; 90 → 11 (виден только
ближний глаз); 120 → 4; 180 → 4 (волосы и заколка, кожи черепа и черт нет);
240 → 4.

**Диагностика приведена к кадру.** `patchWeights` считала гейт сама и не
учитывала видимость — то есть врала относительно рендера. Вычисление гейта
вынесено в одну функцию `patch_gate()` (кольцо → видимость → состояние),
которую используют и рендер, и диагностика.

**Регистрация волос — измеренная, по каждой колонке.** Центр массы волос
совмещается с центром массы головы ДАННОЙ колонки, масштаб — `HAIR_VOLUME`
(1.34) от высоты головы. Раньше посадка была общими константами, и на
профилях кожа черепа выходила поверх волос. Замером проверено, что «окна» под
лицо у боба НЕТ: замкнутая прозрачная область внутри массы — 98..222 px из
~20 000, то есть это не окно, а щели между прядями; поэтому схема «боб поверх
черепа с окном под лицо» на этих ассетах не работает.

## 10. Аудит автора спецификации: что принято и что сделано

Прочитан `from_agent_to_agent.md` (аудит от автора спецификации). Принято:

* раздельные статусы (`container_valid`, `geometry_fit_valid`,
  `anchor_visual_accepted`, `non_anchor_tests_passed`, `pitch_supported`,
  `full_body_supported`) — реализованы в bake-отчёте;
* при нулевой вариансе anchors: `total_variance`, `measured_rank`,
  `retained_variance_ratio=null` вместо «100 %»; ранг формата отделён от
  измеренного; предупреждение о том, что манифолд не обучен;
* **landmarks измеряются внутри изолированных кропов**
  ([tools/pink_landmarks.py](tools/pink_landmarks.py)): верх черепа, ширина по
  вискам, подбородок, углы глаза по линии века, центр/радиус радужки, центры
  брови/носа/рта + профиль кожи по строкам. Overlay для глазной проверки:
  `authoring/pink.landmarks.png`;
* **посадка деталей — от landmarks ДАННОЙ chart**, а не от глобального синуса:
  линия глаз = измеренная линия висков, ширина = доля измеренной ширины черепа,
  нос/рот — доли измеренной высоты головы;
* **видимость near/far — по замеру**: деталь скрывается, если её точка не
  попадает в измеренную область кожи лица.

Реестр дефектов для передачи: [HANDOFF_DEFECTS.md](HANDOFF_DEFECTS.md).

## 11. Полный рост: что исправлено в рантайме

1. **Атлас**: `shelf_pack` сортировал картинки по высоте, но возвращал
   размещения в новом порядке — каждый патч получал чужой прямоугольник
   атласа. Теперь размещения возвращаются в исходном порядке (проверено
   арифметикой: голова 1.02 H, торс 1.45 H, ноги 1.15 H).
2. **Канвас**: рантайм делал канвас строго квадратным и игнорировал высоту из
   манифеста — всё ниже 512 px не рисовалось. Теперь аспект берётся из
   манифеста (512×1024), проверено `pixels()` = 524288.
3. Пределы: патчи 512, кольца 64 (полный персонаж — 265 патчей, 26 колец).

Кадры ключевых видов: 26 патчей / 208 треуг. на фронте, 3.5–4.8 мс raster;
на 180° — 16 патчей (волосы и воротник, лица нет).

## 12. Состояние на конец сессии (для продолжения)

**Что собрано и проверено**

* 12 yaw-колонок + полный персонаж: 262 патча, 26 колец, канвас 512×1024,
  атлас 4096², контейнер `assets/pink_full_v4.r2d4`;
* движок: не квадратный канвас по аспекту манифеста, текстура/спрайт по
  `canvas_w×canvas_h`, provenance по обеим осям, пределы патчей 512 / колец 64;
* видимость §7 работает: на 180° рисуются только волосы и воротник (лица нет);
* **метрика формы**: `tools/pink_profile_metric.py` — профиль силуэта считается
  ВНУТРИ рантайма (без HUD) и сравнивается с рефом по 64 зонам роста.

**Текущее число**: RMS профиля **0.1387** (с работающей маской `clip_rect`; без маски 0.1632) (в начале серии «по метрике» — 0.3005).

**Порядок дальнейших шагов**

1. Профиль: сузить зону 0.33, не задев 0.50; сузить макушку (0.00).
2. Цель RMS < 0.10 — тогда силуэт перестанет расходиться с рефом.
3. §4-C: реальные correspondences (одни semantic controls для совместимых
   видов) → `measured_rank` станет ненулевым (сейчас манифолд — хранилище
   констант).
4. §21: веса фон Мизеса вместо smoothstep-колец; §25: глубина как функция
   `Z=μ_Z+U_Z a_Z` вместо констант.
5. §56: blind-angle test (7.3°, 19.7°, 37.5°, 58.2°, 103.4°, 147.8°, 177.1°,
   238.6°, 319.3°) и проверка второй половины круга.

## 13. §4-C: почему манифолд вырожден и что именно надо переделать

Сейчас `measured_rank=0` не потому, что «мало данных», а потому что **структура
сборки не даёт геометрии меняться по ракурсу**:

* каждый патч существует РОВНО В ОДНОЙ колонке (`head_00`, `head_01`, …);
* его 12 keys относятся к 12 anchor-углам, но описывают ОДИН и тот же рисунок,
  поэтому все 12 значений совпадают → матрица изменений нулевая → ранг 0.

Чтобы §4-C заработал (`q_j` из одних semantic controls, реальный SVD):

1. **Один патч = одна семантическая деталь** (например `head`), а не 12 патчей.
   Его cage/mesh — общий для всех ракурсов.
2. **12 anchor-записей** для этого патча: для каждого yaw-угла — измеренная
   посадка (`dx, dy, sx, sy, rot`), полученная из landmarks соответствующей
   колонки (уже есть: `authoring/pink.landmarks.json`).
3. Тогда матрица `12 × 5` непостоянна → SVD даёт `measured_rank > 0`, а
   Фурье-фит (§4) воспроизводит авторские anchors.
4. Appearance-варианты (12 рисунков колонок) прикрепляются к общему chart и
   смешиваются весами фон Мизеса (§21) — это заменяет нынешний кроссфейд
   отдельных патчей.

Пункты 1–3 — это изменение схемы авторинга (один патч на деталь + массив
anchors), пункт 4 — замена механизма колец. Обе части уже описаны в реестре
(HANDOFF_DEFECTS.md, C1 и C12).
