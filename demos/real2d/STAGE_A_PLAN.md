# Real2D v4 — план стадии A (head-only CPU proof)

Рабочий план к [REAL2D_V4_SPEC.md](REAL2D_V4_SPEC.md) §19 A. Здесь только то,
что делаем сейчас, чем это доказывается и что **не** делаем. Спецификация
остаётся контрактом; этот файл — её исполняемый срез, и он не отменяет ни одного
MUST.

## 1. Цель стадии A

Детерминированный CPU-рендер головы из 16 авторских RGBA-компонентов
(`assets/head_components_candidate_v1.png`): полный круг yaw, pitch = 0,
12 geometry anchors, Fourier K=3, L=0. Каждый показанный ракурс **вычислен**;
готовых полнофигурных кадров в рантайме нет.

Что уже сделано до кода:

* лист проверен кодом ([verify_head_sheet.py](verify_head_sheet.py)): 1254×1254
  RGBA, фон прозрачный, 16 непустых клеток, содержимое клеток не пересекается;
  сетка **не** целочисленная (клетка 313.5 px) — rect'ы берутся из пикселей, а
  не из деления листа;
* из листа извлечены rect'ы компонентов:
  `assets/head_components_candidate_v1.rects.json`;
* аудит движка и SDK выполнен (см. §6).

## 2. Решения и почему

| Решение | Причина |
|---|---|
| Рантайм — новый нативный модуль `src/real2d4.c` + `engine.real2d.*`, обёртка `src/highlevel/real2d.js` | горячий путь обязан быть нативным (PHILOSOPHY §2.5); существующего инверсно-барицентрического растеризатора в движке нет, а z-buffer v3 для слоёв по псевдоглубине не подходит |
| Растеризатор пишем: инкрементальные edge-функции по обеим осям, top-left fill rule, UV на вершине, билинейная выборка, clamp | в `src/rotsprite3.c` растеризация аффинная, шагает по x и не имеет top-left правила; в `src/rotsprite_math.c` — инверсия квада, а не треугольников |
| Переиспользуем: пул потоков `rot_parallel`, `R3Work`-паттерн scratch, `r2d_texture_create_rgba` / `r2d_texture_upload_region` + `touched`, канон валидации | не плодить второе (правило 1); частичная загрузка области уже отработана в v3 |
| Контейнер `.r2d4` — ZIP **store-only**: писатель Python, читатель C ~150 строк | спека §13 просит ZIP; writers/readers в проекте нет, deflate тянул бы зависимость. Метод 1 в v1 отвергается явной ошибкой |
| Baker — Python (`demos/real2d/tools/`), а не SDK C | авторинг работает с PNG/маской/контурами; numpy/PIL уже используются в `tools/`, `demos/re2d_dust2/`. C-команда `bake-real2d` в SDK — отдельная задача после стадии A |
| Композиция: linear RGB, premultiplied alpha, вывод в sRGB | спека §3; на GPU по-прежнему straight-alpha, но CPU-композит делает движок сам, до загрузки текстуры |
| Манифолд на уровне **параметров патча** (перенос/масштаб/поворот), а не сырых вершин cage | chart'ы имеют разную топологию; спека §4 запрещает складывать несопоставимые индексы. Заявленное упрощение MVP: базовый cage каждого chart фиксирован, манифолд описывает его размещение. Переход к per-vertex базам — следующая стадия |
| Обе стороны yaw | в листе есть только right-facing 3q/profile. Левая сторона получается зеркалом **только для патчей, объявленных симметричными** (`mirror: "x"` в authoring manifest); нос/глаз 3q зеркалятся вместе с лицом. Отражение всего персонажа «по умолчанию» запрещено (спека §10) и в манифесте не объявляется |

## 4. Доказательства стадии A (что именно проверяем)

1. **Петля yaw:** `θ` и `θ+2π` дают побитово одинаковый кадр (720 шагов по
   кругу, pitch −30/0/+30 — для стадии A значим 0).
2. **Шов:** θ = −ε, 0, +ε, 2π−ε, 2π, 2π+ε (ε = 1e−4) — скачок изображения и
   производной в пределах допуска спеки.
3. **Не-анкорные углы:** фиксированный список (33.7°, 58.2°, 103.4°, 177.1°,
   238.6°, 319.3°, 37.5°) рендерится без отказов, с ненулевым покрытием.
4. **Provenance:** для выбранных пикселей доступна цепочка
   patch → triangle → UV → atlas samples; сохраняется в отчёт.
5. **Мутация источника:** зануление атласа → прозрачный кадр; смена палитры
   одного патча → меняются только его пиксели.
6. **Hard validator:** ни одного видимого вывернутого/вырожденного
   треугольника; при нарушении — отказ оценки с диагностикой, а не «починка».
7. **Визуальный семантический review** кадров 0/45/90/135/180/225/270/315°:
   одно лицо, максимум два глаза, один нос, один рот, back без лица, профиль
   читается.
8. **Производительность:** замер `evaluate` и растеризации на 512×512,
   запись конфигурации (без обещаний вне объявленной машины).

Отрицательный результат — тоже результат: если угол/патч не проходит, это
попадает в `bake/report.json` с перечислением углов, а не «подкрашивается».

## 5. Чего в стадии A нет (и что не заявляем)

* pitch вне `[−30°, 30°]` → `OUT_OF_DOMAIN`; в стадии A pitch вообще не вход;
* полнотелый персонаж, одежда, кисти рук;
* состояния (blink/mouth/gaze) — только если останутся данные и время; иначе
  это стадия D;
* GPU-бэкенд и сравнение с CPU;
* Baker с end-to-end оптимизацией изображения (спека §16 разрешает для MVP
  аналитический fit без image-optimization — это фиксируется в report).

## 6. Что дал аудит (кратко, с опорой на код)

* `src/rotsprite3.c` — аффинная растеризация `raster_tri` без top-left правила,
  шаг только по x; z-buffer вместо порядка слоёв; детерминированный tie-break
  цвета; полосы 48/8, чанки 8192; `R3Work.touched`.
* `src/rotsprite.c` — пул `rot_parallel`, `ensure_pixels`, `dispose`,
  `r2d_sprite_create` + `force_linear`; `touched` → `r2d_texture_upload_region`.
* `src/render.c` — `r2d_texture_create_rgba` (:397), `r2d_texture_upload_region`
  (:424), straight-alpha блендинг (:96-105) — premultiplied на GPU нет,
  значит премультипликацию делает CPU до загрузки.
* SDK: писателя ZIP и SHA256 в C нет; для C-бейкера потом придётся либо
  реализовать store-ZIP/SHA256, либо писать hex-LE как в
  `src/re2d_world_bake.c` (устоявшийся в проекте вариант). Стадию A это не
  блокирует: бейкер сейчас на Python.
* Регистрация: `src/CMakeLists.txt` (список источников) и
  `src/script.c` (`r2d__make_engine`, рядом с `r2d_re2d_install`).

## 7. Порядок работ

1. authoring: патчи, cage, gate'ы, ключевые кадры → `head.authoring.json`;
2. bake: PCA + Fourier (K=3, L=0) + сборка `.r2d4` + отчёт;
3. C: загрузчик контейнера, evaluation, cage warp, растеризация, композит;
4. `$`-модуль `real2d.js` + демо `demos/real2d` (текстура → спрайт → RmlUi HUD);
5. доказательные тесты §4, документация модуля, CHANGELOG.

Каждый шаг заканчивается рабочей сборкой и прогоном тестов; следующий не
начинается, пока текущий не зелёный (AGENT_IMPLEMENTATION_RULES, «Рабочий цикл»).

## 8. Состояние выполнения (2026-10-10)

Пункты 1–5 порядка работ сделаны; стадия A проходит доказательный прогон
[tests/agent/real2d_test.py](../../tests/agent/real2d_test.py):
петля yaw (θ и θ±2πk дают один кадр), шов, не-анкорные углы, provenance,
мутации источника, `fill rule`, полный круг 24 шагами. Юнит-тест модуля —
[tests/js/real2d_test.mjs](../../tests/js/real2d_test.mjs).

| Что | Где |
|---|---|
| Патчи, cage + bindings, UV, гейты, 12 anchors | `authoring/head.authoring.json`, [tools/author_head.py](tools/author_head.py) |
| Манифолд `q(θ)=μ+B·a(θ)`, ранг 6, `K=3`, ошибка anchors 0.011 H | `assets/head_real2d_v4.bake.json` |
| Контейнер `.r2d4` (ZIP store-only, CRC32, детерминированный) | [tools/bake_real2d.py](tools/bake_real2d.py) |
| Рантайм: load → evaluate → warp → растр → композит → текстура | [src/real2d4.c](../../src/real2d4.c) |
| Обёртка `$` и тег `<real2d>` | [src/highlevel/real2d.js](../../src/highlevel/real2d.js), [docs/highlevel/real2d.md](../../docs/highlevel/real2d.md) |
| Демо и хуки доказательств | [demos/real2d/main.js](main.js) |

**Что уточнено во втором проходе:**

* нормализованная композиция группы лиц: два варианта по 0.5 дают alpha 1.0, а
  не 0.75 — ушла «полупрозрачная голова» на переходах;
* переходы сужены до быстрого свапа (лицо 1.5°, глаза 3°, нос/рот 4°, волосы
  6–10°): «двойное лицо» осталось только в узком окне вокруг границы;
* provenance пишется только для непустых сэмплов (иначе карта покрытия врала) и
  переаллоцируется при смене размера растра (был выход за границу буфера);
* добавлена структурная диагностика `engine.real2d.patchWeights` — гейты и
  параметры каждого патча на заданном угле;
* замер до оптимизации: 23.9 мс/кадр при 512×512 и 5.6 мс при 256×256;
* фазовая диагностика `info().ms` показала, что узкое место — растеризация
  (20.5 из 24.9 мс), а не очистка буферов: очистка по грязному прямоугольнику
  сама по себе дала ±0, зато убрала следы предыдущего угла в текстуре
  (загрузка идёт по объединению прошлого и текущего прямоугольников);
* растеризация распараллелена через общий пул движка (`r2d_rot_parallel`,
  тот же, что у синтеза v3): **13.5 мс** при 512×512 и **4.3 мс** при 256×256,
  фаза растеризации 20.5 → 6.5 мс. Детерминизм сохранён: треугольники не
  пересекаются по пикселям (правило top-left), результат не зависит от
  планировщика — проверено равенством хешей и петлёй yaw;
* доказательный тест нашёл регрессию оптимизации: буферы кадра перестали
  обнуляться при выделении, и в кадр попадала неинициализированная память
  (зануление атласа больше не давало пустой кадр). Исправлено.

**Что осталось и не выдаётся за сделанное:**

1. **В узком окне перехода (≈±1.5°) видно наложение двух рисунков.** Это
   остаток того же корня: варианты — разные изображения, а не один chart с
   appearance-слоями. Настоящее решение — общий chart с согласованной
   топологией и appearance-вариантами в общих UV (спека §3, §6), то есть
   следующая стадия, а не настройка констант.
2. **Профиль беднее фронта.** Чёлка гаснет к 80°, поэтому на профиле волосы
   даёт только масса сзади и прядь; left-facing appearance в исходном листе
   отсутствует (правая сторона получена зеркалом объявленных симметричных
   патчей — пункт «left-facing appearance review» ещё требует глазной проверки).
3. **Pitch не вход.** Домен стадии A — `pitch = 0`; ±30° требует данных, которых
   в листе нет.
4. **Полнотелого персонажа нет.** Одежда, руки, ноги, attachment graph — стадия C
   спецификации.
5. **Производительность не дотягивает до цели спеки.** 13.5 мс/кадр при
   512×512 (цель ≤1 мс). Что уже сделано: пул потоков (2.5× на растеризации),
   очистка и загрузка по грязному прямоугольнику, фазовая диагностика. Что
   осталось: слияние композита с растеризацией (сейчас три прохода),
   SIMD-выборка атласа, отказ от промежуточного слоя для патчей без клипа.
