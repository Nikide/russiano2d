# Реестр дефектов Real2D v4 / pink_v4

Документ для передачи автору спецификации и ассетов (handoff
`from_agent_to_agent.md`). Каждая запись: что не так, **чем измерено**, что
делает реализация сейчас и что нужно, чтобы закрыть. Без «уже исправлено» без
замера.

Легенда владельца: **ASSET** — непригодность исходного artwork или разметки
(зона автора ассетов); **SPEC** — пробел/противоречие в спецификации;
**IMPL** — упрощение или отсутствие в моей реализации.

---

## A. Ассеты и разметка (ASSET)

### A1. Нет общей рамки, сетка не соблюдается
Клетки номинальной сетки не совпадают с содержимым: 147.8 / 181.0×120.7 /
128×170.7 / 167.8×130.2 px, содержимое крупнее клетки и выходит в соседей.
Измерено `tools/inspect_sheet.py`. Следствие: «взять клетку (row, col)» нельзя
ни для геометрии, ни для UV. Нужно: re-export с гарантированным margin или
per-cell bbox в metadata каждого листа.

### A2. Слои внутри листа не выровнены по клетке
Каждый ряд нарисован по центру своей клетки; общей рамки у слоёв нет. Слой
`hair_back` клетки (1, c) не знает, где череп из клетки (0, c). Измерено
сборкой: наивная посадка «по номеру клетки» кладёт голову сверху, волосы снизу.

### A3. У ряда лица клетка содержит сборку, а не одну деталь
В клетке глаза лежат глаз + бровь + линия века; в клетке «радужка» — радужка и
блик. bbox содержимого клетки глаза = (74, 0, 181, 120) при клетке 181×121.
Нужно: отдельные элементы на отдельные ряды либо mask/metadata.

### A4. У `hair_back` НЕТ выреза под лицо
Проверено замером замкнутой прозрачной области: 98..222 px из ~20 000 — это
щели между прядями, а не окно. Схема «масса волос поверх черепа с окном под
лицо» на этом artwork невозможна. Нужно: либо отдельный слой волос «перед
черепом» с настоящим вырезом, либо явный scalp-root landmark на листе.

### A5. Ракурсная конвенция требует ручной переаннотации
Совпадение «колонка = yaw по индексу» не проверено генератором. Измерено:
радужка исчезает на 150°, глаза на 180° — согласуется с конвенцией
0/30/…, но exact angle аннотация отсутствует в metadata листов.

### A6. Бледные ореолы вокруг деталей
Alpha 1..15 занимает 25–30 % площади клетки. Кроп по такому ореолу берёт дымку
(чёлку «не доводит» до бровей, лоб выглядит плешивым). Обход в реализации:
кроп по плотной альфе (`SOLID_ALPHA=48`) — но это костыль вместо чистых ассетов.

### A7. Шит тела: слои смешаны с одеждой
Не проверялось замером (стадия C не начата). Из описания пакета: верхние руки
содержат рукава, бёдра — фрагмент юбки, обувь — часть гольфа. Нужны owner и
masks, иначе одежда дублируется.

## B. Спецификация (SPEC)

### B1. `v=(cosθ,sinθ,u)` не предписывает цилиндрическую модель лица
§2 задаёт периодическое кодирование входа. Реализация вывела из него посадку
глаз `x=R·sin(φ+θ)` — это догадка реализации (см. C2), а не требование
спецификации. Нужно: явный раздел «какие facial landmarks обязательны и как они
связаны между chart».

### B2. Нет маски века для клипа радужки
§8 требует `A/A0` и клип; §7 говорит про occlusion masks, но контейнер не имеет
поля «клипать по раскрытию века». Сейчас есть только `clip_to: face` (силуэт
лица), чего для радужки недостаточно. Нужно: поле mask/chart id.

### B3. Не определено, что делать при нулевой дисперсии anchors
Аудит §3 требует `total_variance=0`, measured rank 0, ratio = n/a. В
спецификации этого правила не было — реализация вывела его из аудита.

## C. Реализация (IMPL)

### C1. «View manifold» — хранилище констант
Измерено: `total_variance=3.5e-30`, `measured_rank=0`, `format_rank=1`.
Keys каждого патча одинаковы для всех 12 yaw. Это не обученный манифолд.
Статус `geometry_fit_valid=false` — выставляется автоматически.

### C2. Цилиндрическая эвристика вместо authored face landmarks
`x=0.5·sin(φ+yaw)`, ширина `∝cos(φ+yaw)` — догадка. Заменяется измеренными
landmarks chart (`authoring/pink.landmarks.json`).

### C3. Screen-space crossfade вместо §6
Переходы — `ring_weight` (smoothstep) между патчами соседних колонок, то есть
кроссфейд зарегистрированных, но не приведённых в общую UV изображений.
§6 (softmax в общей canonical chart) не реализован.

### C4. Глубина — авторские константы
§9 требует `d_i=Σ c_ikl F_k T_l`. Сейчас `depth` — числа из таблицы авторинга.

### C5. Регистрация волос по центру масс
`HAIR_VOLUME=1.34` + совмещение центроидов вместо scalp roots/висков/силуэта.

### C6. Диагностика `patchWeights` расходилась с кадром
Была своя копия вычисления гейта без видимости — то есть как доказательство
не годилась. Исправлено: общий `patch_gate()`.

### C7. `ring_weight`: `fade` трактовался как полуокно
Вес в anchor-точке был 0.5, рисовались две колонки сразу (двойные черты,
бледность). Исправлено: `fade` — полная ширина перехода.

### C8. Пики весов стояли на границах, а не на anchor'ах
Границы колец обязаны быть серединами между ключами (`a_k = key_k − fade/2`).
Исправлено.

### C9. `owner_group` вне словаря рантайма
Незнакомое имя трактовалось как 0 — «группа лица», которая копится суммой;
пересекающиеся слои выгорали в белый. Исправлено в авторинге, но рантайм
по-прежнему молча маппит незнакомое имя в 0 — нужен явный отказ загрузки.

### C10. Baker навязывал единицу H
`UNIT_PX=380`, `origin=(256,72)` были жёсткими; теперь читаются из authoring.

### C11. Производительность не в цели §17
512²: raster 6–25 мс при цели ≤1 мс p95. Замер конфигурации не полный
(CPU/GPU/OS/backend/build не фиксируются в отчёте).

### C12. Ошибка единиц в посадке (найдена и исправлена сегодня)
Цель детали считалась как `доля × пиксели кропа`, а сравнивалась с канвасом в
единицах H (`HEAD_UNIT_PX=240`). Из-за этого все детали садились примерно в
2.2 раза ближе к центру, чем задумано (глаза — к переносице). Исправлено:
цель считается в единицах высоты головы.

### C13. Масштаб детали по неверной оси
Широкий кроп глаза масштабировался по ВЫСОТЕ и растягивался в полосу через всё
лицо. Исправлено: ширина для глаза/радужки/брови/рта/чёлки/заколки, высота для
носа и прядей.

### C14. Масштаб листов тела не откалиброван (открыто)
Полный персонаж собирается (265 патчей, 2120 треуг., канвас 512×1024, атлас
4096², 26 колец), но кадр негоден: торс огромный, ноги мелкие и дублируются.
Причина: у листов `pink_body_limbs` и `pink_clothing_equipment` СВОЙ масштаб
рисунка, и перевод «доля головы → пиксели слоя» сделан через пиксели кропа
головы, а не через измеренный габарит самого листа. Нужно: измерить на каждом
листе репер (например, ширину торса по линии плеч и высоту торса), выразить
его в единицах высоты головы через анатомическую пропорцию и калибровать все
детали листа одним коэффициентом.

### C15. НАЙДЕНО И ИСПРАВЛЕНО: упаковщик атласа перемешивал патчи
Корень всех «полос вместо торса» и «ног вверху»: `shelf_pack` сортировал
картинки по высоте для плотной укладки, но возвращал размещения в НОВОМ
порядке, а `zip(collected, placed)` сопоставлял их исходному — то есть каждый
патч получал чужой прямоугольник атласа (и чужой artwork в UV). Исправлено:
упаковщик возвращает размещения в исходном порядке. Проверено арифметикой:
`head_00` 110×146 px → 131×174 канваса (1.02 единицы), `torso_00` → 1.45,
`legs_00` → 1.15 — ровно то, что задано в таблице.

### C15b. Исходный симптом (оставлено для истории)
Кадр полного роста: торс рисуется полосой высотой ~0.5 канваса, ноги уходят
вверх, детали накладываются друг на друга. Числа известны: канвас 512×1024,
единица 170 px (1 единица = высота головы), `torso` задан высотой 1.45 единицы
= 246 px, но на кадре он ~500 px — значит масштаб патча тела считается по
другой базе, чем та, которой измеряется цель. Проверять надо ровно одно:
`source_px_per_unit` для листов body/cloth обязан быть `src_dim_px / размер_в_H`
с одним и тем же H = `unit_px`, а локальные координаты патча — в тех же
единицах (как у головы). Пока это не сойдётся, полный кадр предъявлять нельзя.

### C16. НАЙДЕНО И ИСПРАВЛЕНО: рантайм игнорировал высоту канваса
`ensure_scratch(a, size)` делал канвас строго квадратным, а высота из манифеста
использовалась только для валидации. Следствие: у полного роста всё ниже
512 px (ноги, ботики) просто не рисовалось, а `pixels()` возвращал 262144
значения вместо 524288. Исправлено: канвас не квадратный, аспект берётся из
манифеста (`canvas.width/height`), ширина кадра = опция `size`, высота
считается по аспекту; валидация допускает не квадратный канвас в пределах
лимитов. Проверено: `pixels()` = 524288 (512×1024), ноги на канвасе (256,640)
имеют цвет, боты ниже 860 px — вне фигуры.

### C17. НАЙДЕНО И ИСПРАВЛЕНО: provenance считался только по ширине
Проверка переаллокации буферов владения пикселем шла как `prov_size !=
canvas_w`, поэтому при канвасе 512×1024 буферы оставались от 512×512 и внизу
кадра «владелец» пикселя был мусорным: зонд показывал у носа, головы и волос
bbox до y=1016. Исправлено: следим за обеими осями (`prov_w`, `prov_h`),
calloc по фактическому числу пикселей. Проверено зондом: ложные bbox исчезли,
голова 80..232, блуза 248..496, юбка 448..608, ноги 640..800, боты 768..832.

### C18. Разметка рядов листа тела сбита (открыто)
Кластеризация рядов `centers_1d` на `pink_body_limbs` даёт неверные границы:
ряд 4 (бёдра) представлен ОДНОЙ колонкой, поэтому кольцо `hips` получило одну
запись (`hips_11`, a=b=0) и на всех углах рисуется одно и то же бедро. Нужно:
для листов тела/одежды переаннотировать ряды (у них регулярная сетка) и
проверить, что каждая семантика имеет 12 колонок.

### C19. НАЙДЕНО И ИСПРАВЛЕНО: текстура/спрайт оставались квадратными
Нашлось при сравнении с рефом side-by-side: кадр 512×1024 считался верно (буфер,
provenance), но текстура для GPU и спрайт создавались как size×size, поэтому на
экран попадали только верхние 512 строк — фигуру «резало» по груди. Исправлено:
текстура и спрайт создаются по `canvas_w × canvas_h`, слежение за размером идёт
по обеим осям (`tex_size`, `tex_h`). После правки полный рост виден целиком:
голова → матроска → юбка → чулки → боты.

### C20. Дубликаты деталей (закрыто частично)
`boot_l`/`boot_r` дублировали обувь (в кропе ног она уже есть), `hips` —
фрагмент юбки (в BODY_ASSETS это отмечено как известная особенность листов).
Убраны из таблицы. Осталось проверить `belt` (в кадре видна вторая плиссировка
на поясе).

### C21. Проба на референс: IoU силуэта 0.29 (базовая точка)
Сравнение кадра движка с фронтальной фигурой рефа даёт IoU силуэта **0.29**

| 8 | скелет по ИЗМЕРЕННЫМ landmarks рефа (плечи 0.30 роста, талия 0.42, подол 0.58, колено 0.66, стопа 0.87) | 0.329 ↓ |

Итог: лучшая измеренная конфигурация — 6c (0.348), она и оставлена в коде.

**Важное про саму метрику.** IoU считается после нормировки каждого силуэта по
его собственному габариту, поэтому он НЕ чувствует абсолютных пропорций: скелет
с измеренными landmark'ами даёт 0.329, со старыми константами 0.348 — разница
в пределах шума формы. Для следующей итерации нужна метрика, чувствительная к
пропорциям: ошибка **относительных** положений landmarks (плечо/талия/колено/
стопа как доли роста) между кадром и рефом, а не глобальный IoU силуэта.
Сегментная калибровка принципиально правильная, но её границы (плечо 1.18,
подол 3.30 и т. д.) были моими догадками, а не измерениями — чтобы она
заработала, границы сегментов надо ИЗМЕРИТЬ на рефе (плечо/локоть/талия/бедро/
колено/стопа), а не назначать.

Вывод: обе гипотезы 6a/6b сделали кадр ХУЖЕ по метрике, поэтому откачены.
Правильный путь для одежды/тела — не подбор оси масштаба и не смена режима
кропа, а **landmark-калибровка внутри каждого кропа** (плечо/локоть/талия/бедро
как измеренные точки, как это уже сделано для головы и лица). Тогда масштаб и
посадка перестанут быть угадыванием.

### C23. Landmark-метрика пропорций (новая, работает)

Инструмент [tools/pink_metric.py](tools/pink_metric.py) сравнивает кадр и реф по
положениям скелетных ориентиров как ДОЛЕЙ РОСТА (глобальный IoU этого не умеет).

Первый замер (yaw 0, лучшая конфигурация):

| ориентир | движок | реф | Δ |
|---|---|---|---|
| шея | 0.228 | 0.000 | +0.228 |
| плечи | 0.318 | 0.135 | +0.183 |
| талия | 0.511 | 0.180 | +0.331 |
| юбка | 0.606 | 0.503 | +0.103 |
| подол | 0.608 | 0.598 | +0.010 |

Средняя ошибка **0.171 роста** (max 0.331). То есть вертикальная раскладка
фигуры действительно далека от рефа: у меня голова с волосами занимает заметно
большую долю, а талия уезжает вниз.

Честное замечание к самому инструменту: правило «талия = минимум ширины между
плечами и 0.6 роста» на РЕФЕ попадает в шею (0.18 выглядит как шея, а не
талия). Правило надо уточнить (искать минимум ПОСЛЕ начала юбки), иначе
сравнение смещено. Это следующая правка метрики.

### C24. Метрика пропорций: две версии правил и их артефакты

1. **По ширине силуэта.** «Плечи = максимум ширины в верхней трети» на рефе
   ловит **волосы** (у рефа волосы шире плеч), «шея = минимум до плеч» ловит
   макушку. Числа: шея 0.228 против 0.000, плечи 0.318 против 0.135 — то есть
   ориентиры смещены артефактом, а не фигурой.
2. **По цветовым полосам** (блуза = светлые пиксели внутри силуэта, низ =
   тёмные). Сравнимо: полоса блузы у движка **0.319..0.584** роста. Но на рефе
   светлыми оказываются и блики обуви, поэтому полоса тянется до 1.0 —
   правило надо ограничить цветом блузы (тёплый белый), а не «value > 200».

Что уже измерено устойчиво и совпадает в обеих версиях: **верх фигуры у меня
начинается слишком низко** (блуза с 0.32 роста против ~0.11 у рефа), тогда как
юбка стоит верно (Δ −0.015 по ширине). Значит следующая правка — поднять блок
«шея/плечи/блуза» примерно на 0.2 роста (≈1 единица головы) и укоротить вылет
волос вверх; пропорции низа не трогать.

### C25. Рабочая метрика: профиль ширины силуэта по строкам

Хрупкие ориентиры («где плечо») выброшены. Метрика нормирует оба силуэта по
росту и сравнивает профиль ширины в 64 зонах: RMS и самая расходящаяся зона.
Артефактов правил нет — сравнивается форма.

| итерация | изменение | RMS |
|---|---|---|
| 12a | исходное состояние раунда | 0.254 |
| 12b | низ фигуры (бёдра/колено/щиколотка) опущен на 0.55 единицы головы | 0.237 ↓ |
| 12c | ширины по профилю рефа: блуза 0.95, юбка 1.55 единицы (масштаб по ширине) | **0.210** ↓ |

| 13 | волосы сверху сужены (1.44→1.10), юбка расширена (1.55→1.85), боты убраны, ноги удлинены до подошвы | **0.182** ↓ |

### C54. §4-C выполнен на уровне данных: манифолд перестал быть константой

Ключи каждого патча больше не дублируются: они берутся из ИЗМЕРЕННЫХ посадок
всех 12 колонок той же семантики (§4-C: «одни semantic controls для совместимых
видов»). Рендер не изменился (кольцо активирует патч только на его углу), но
матрица изменений стала непостоянной:

| показатель | до | после |
|---|---|---|
| `total_variance` | 3.5e-30 | **89.44** |
| `measured_rank` | 0 | **11** |
| `format_rank` | 1 | 8 |
| `anchor_reconstruction_max_abs` | 0.0 | **0.2195** |
| `geometry_fit_valid` | false | false (по делу: фит не дотягивает anchors) |
| RMS профиля (форма) | 0.1386 | **0.1349** ↓ (на переходах интерполируются измеренные посадки) |

Теперь `geometry_fit_valid=false` — это НАСТОЯЩИЙ сигнал, а не заглушка: манифолд
обучен (11 измеренных мод), но фит K=3 и ранг 8 не воспроизводят авторские
anchors с ошибкой 0.22 единицы. Следующий шаг измерим: поднимать K (порядок
Фурье) и/или потолок ранга, пока `anchor_reconstruction_max_abs` не уйдёт
к нулю, и только потом менять что-то ещё.
