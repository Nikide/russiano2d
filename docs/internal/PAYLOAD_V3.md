# Груз игры v3: случайный доступ, mmap и инкрементальная распаковка

> **Внутренний документ.** Контейнер груза (`src/payload.c`, формат — в
> [`src/payload.h`](../../src/payload.h)) сегодня читается целиком: v1 — без
> сжатия, v2 — **одним кадром zstd**. Версия 3 в этом документе только
> спроектирована; сериализация ещё не реализована, `R2D_PAYLOAD_VERSION_MAX`
> остаётся 2, а неизвестная версия отвергается кодом
> `R2D_PAYLOAD_UNKNOWN_VERSION`.

## 1. Зачем v3: чем плохи v1/v2 сегодня

Текущая раскладка (см. `payload.h`):

```
v1: [magic][version=1][entry_len][entry][count][файлы…]
v2: [magic][version=2][flags][raw_size u64][zstd-кадр тела]
```

Проблема не в шифровании (ChaCha20-Poly1305 остаётся как есть), а в том, что
**всё тело — один блок**:

1. **Нет случайного доступа.** Чтобы отдать один звук или шрифт, движок обязан
   распаковать весь груз: zstd-кадр не даёт распаковать «с середины» без
   индекса. Время старта растёт линейно по размеру всех ассетов, даже если
   игра в этом запуске использует 2 % из них.
2. **Пиковая память = весь груз.** `plain` — это копия всего тела в куче.
   Для проекта с текстурами/музыкой это десятки-сотни мегабайт, которые
   заняты постоянно, хотя SDL_mixer читает звук потоком, а картинки грузятся
   по требованию.
3. **Дорогая ошибка.** Повреждён один байт сжатого кадра — не читается весь
   груз (это честно, но слишком грубо): непонятно, какой файл испорчен, и
   нельзя продолжить с остальными.
4. **Нельзя обновлять по частям.** Любое изменение ассета пересобирает и
   пересжимает весь контейнер; инкрементальных патчей нет.
5. **Запуск читает весь exe.** `r2d_payload_attach_self` делает
   `SDL_LoadFile(path, &file_size)` — то есть копирует в память **весь
   исполняемый файл**, включая сам движок (десятки мегабайт), только чтобы
   прочитать футер и контейнер в конце. На слабых машинах и в вебе это заметно.
6. **Нельзя отдать данные без копии.** Сейчас под этот контракт уже есть
   `MIX_LoadAudioNoCopy` и `r2d_vfs_read`, но v1/v2 всё равно вынуждают держать
   один большой буфер.

Цели v3: O(1) поиск по имени, чтение/распаковка **только нужного чанка**,
работа поверх `mmap`/`pread` без чтения всего exe, совместимость чтения v1/v2,
и возможность инкрементального обновления в будущем.

## 2. Раскладка v3

Всё многобайтовое — **little-endian**, как в v1/v2. Смещения v3 — от начала
контейнера (не от начала файла): футер по-прежнему лежит в конце exe и хранит
`offset`/`size` контейнера, так что приписывание к другому бинарнику ничего не
ломает.

```
┌──────────────────────────────────────────────────────────────┐
│ HEADER (фиксированный, 64 байта)                              │
├──────────────────────────────────────────────────────────────┤
│ TOC: FileEntry[file_count]        (по 48 байт)                │
├──────────────────────────────────────────────────────────────┤
│ ChunkEntry[chunk_count]           (по 40 байт)                │
├──────────────────────────────────────────────────────────────┤
│ HASH-INDEX: отсортированные пары (hash64, file_id)            │
├──────────────────────────────────────────────────────────────┤
│ CHUNKS: сжатые/сырые блоки файлов (выравнивание 8 байт)       │
└──────────────────────────────────────────────────────────────┘
```

### 2.1. HEADER (64 байта)

| Смещение | Размер | Поле | Смысл |
|---:|---:|---|---|
| 0 | 4 | `magic` | `0x33443252` («R2D3»), отличается от v1/v2 |
| 4 | 2 | `version` | `3` |
| 6 | 2 | `header_size` | `64` (запас на расширение) |
| 8 | 4 | `flags` | битовые признаки контейнера |
| 12 | 4 | `method_default` | метод сжатия по умолчанию (0 = raw) |
| 16 | 4 | `file_count` | число файлов в TOC |
| 20 | 4 | `chunk_count` | число чанков |
| 24 | 8 | `toc_offset` | смещение FileEntry[] |
| 32 | 8 | `chunk_offset` | смещение ChunkEntry[] |
| 40 | 8 | `hash_offset` | смещение HASH-INDEX |
| 48 | 8 | `data_offset` | начало области CHUNKS |
| 56 | 8 | `body_size` | полный размер контейнера (для проверок) |

`flags` (пока известны):

* `1` — контейнер зашифрован (AEAD-обёртка снаружи, как в v2);
* `2` — HASH-INDEX отсортирован (обязателен в v3);
* `4` — чанки выровнены на 8 байт;
* `8` — разрешены chunk'и с разными методами сжатия.

Неизвестные биты `flags` — ошибка `R2D_PAYLOAD_FLAGS`, как и в v2.

### 2.2. FileEntry (48 байт)

| Смещение | Размер | Поле | Смысл |
|---:|---:|---|---|
| 0 | 8 | `hash64` | FNV-1a 64 от нормализованного пути (или xxh3 — см. §2.5) |
| 8 | 4 | `path_off` | смещение строки пути от начала контейнера |
| 12 | 4 | `path_len` | длина пути без NUL |
| 16 | 8 | `raw_size` | полный размер файла до сжатия |
| 24 | 4 | `first_chunk` | индекс первого ChunkEntry |
| 28 | 4 | `chunk_count` | сколько чанков у файла (для потокового чтения) |
| 32 | 4 | `method` | метод по умолчанию для файла (совпадает с чанками, если `1`) |
| 36 | 4 | `flags` | `1` — точка входа, `2` — utf8-путь, `4` — файл целиком один чанк |
| 40 | 8 | `reserved` | 0 (запас, проверяется как 0) |

### 2.3. ChunkEntry (40 байт)

| Смещение | Размер | Поле | Смысл |
|---:|---:|---|---|
| 0 | 8 | `offset` | абсолютное смещение от начала контейнера |
| 8 | 4 | `compressed_size` | сколько байт занимает блок в контейнере |
| 12 | 4 | `raw_size` | сколько байт после распаковки |
| 16 | 4 | `file_id` | индекс файла в TOC |
| 20 | 4 | `method` | `0` raw, `1` zstd, `2` zstd-dict (зарезервировано) |
| 24 | 4 | `flags` | `1` — последний чанк файла, `2` — можно mmap без копии |
| 28 | 4 | `crc32` | CRC32C распакованных данных (необязателен при `0`) |
| 32 | 8 | `reserved` | 0 |

Чанк — единица распаковки и кэша. Для маленьких файлов это один чанк целиком
(`flags & 4` в FileEntry). Для больших (музыка, атласы) — куски по 64 КиБ…
1 МиБ, чтобы `r2d_vfs_read` мог отдавать данные потоком, а не целиком.

### 2.4. HASH-INDEX

`file_count` пар `[hash64][file_id u32][reserved u32]` (16 байт на файл),
отсортированных по `hash64`. Поиск — бинарный (`O(log n)`), нормализация пути
та же, что в текущем `r2d_payload_find` (точное совпадение, затем basename/
суффикс — см. §2.6). `hash64` считается по **нормализованному** пути:
прямые слэши, без `.`/`..`, без ведущего `./`, в нижнем регистре только если
контейнер собран с `--case-fold`; флаг нормализации пишется в `flags`.

Коллизии `hash64` разрешаются сравнением строк по `path_off`; бинарный поиск
идёт по хэшу, а не по строке, поэтому стоимость не зависит от длины путей.

### 2.5. Методы сжатия

* `RAW=0` — данные лежат как есть, `compressed_size == raw_size`;
* `ZSTD=1` — независимый zstd-кадр на чанк (не «поток», а самостоятельный
  frame), уровень — тот же `R2D_PAYLOAD_ZSTD_LEVEL=19`;
* `ZSTD_DICT=2` — резерв: общий словарь на контейнер (обучается на TOC),
  формат словаря — отдельный чанк с `file_id = 0xFFFFFFFF`.

Независимые кадры на чанк — сознательная цена: теряется ~0.5–1 % сжатия
относительно одного кадра v2, зато появляется случайный доступ и частичная
распаковка. Замер обязателен на реальном грузе до включения v3 по умолчанию.

### 2.6. Сохранение семантики поиска

`r2d_payload_find` обязан вести себя как сегодня:

1. точное совпадение пути — первым;
2. иначе — совпадение суффикса на границе каталога в любую сторону
   (`assets/x.png` ↔ `/opt/game/assets/x.png`, `x.png` ↔ `assets/x.png`);
3. при нескольких кандидатах побеждает **первый по порядку файлов в
   контейнере**.

В v3 это выполнимо: hash-индекс хранит полные пути, точный поиск — бинарный
по хэшу; для суффиксного поиска остаётся basename-таблица (как в текущем
`payload.c`: basename → цепочка file_id в порядке TOC), а внутри цепочки
проверяется то же условие суффикса. Порядок `FileEntry` в TOC — и есть порядок
«первого совпадения», поэтому tie-breaking не меняется.

## 3. Случайный доступ: как читается один файл

```
r2d_payload_v3_open(name):
  normalize(name)
  file_id = hash_lookup(name)              // O(log n) по HASH-INDEX
  fe = FileEntry[file_id]
  if fe.method == RAW and fe.chunk_count == 1:
      return view(fe.offset, fe.raw_size)  // ноль копий
  return stream(fe.first_chunk, fe.chunk_count)
```

`r2d_vfs_read` для больших файлов получает поток: чанки распаковываются по
одному, с ограничением «не больше N чанков в памяти». Для маленьких файлов
(один чанк) поведение прежнее — один буфер, владелец груз.

Кэш чанков (LRU, лимит по байтам) — **необязательная** оптимизация: она не
меняет контракт владения. Если кэш выключен, каждый `r2d_vfs_read` чанка
распаковывает заново; контракт `r2d_vfs_free` остаётся прежним (указатель
внутрь груза/kэша — no-op, буфер с диска — `SDL_free`).

## 4. mmap/seek: запуск без чтения всего exe

Сегодня `r2d_payload_attach_self` делает `SDL_LoadFile` всего бинарника.
В v3 (и это можно сделать **до** реализации v3, отдельным улучшением):

1. Открыть свой exe через `SDL_IOFromFile` (или `open`+`pread`).
2. `seek` в конец, прочитать **только футер** (`R2D_FOOTER_SIZE` байт).
3. Проверить магию/дубль, взять `offset`/`size` контейнера.
4. `seek` на `offset`, читать только контейнер (или маппить его).
5. На POSIX — `mmap(PROT_READ, MAP_PRIVATE)` на диапазон контейнера; на
   Windows — `CreateFileMapping`+`MapViewOfFile`. Ошибка mmap — не приговор:
   фолбэк на `pread`/`SDL_IO` по чанкам.

Важно: **не** отдавать игру данные по указателю в mmap без учёта платформы
(веб/быстрый старт без файла) — `r2d_vfs_read` должен уметь вернуть копию,
если регион не маплен. Признак «данные можно отдавать без копии» —
`ChunkEntry.flags & 2`; иначе груз копирует чанк в кучу (владелец — груз).

Шифрование: AEAD в v2 шифрует всё тело одним тегом. Для случайного доступа v3
шифрует **каждый чанк отдельно** (nonce = базовый nonce ⊕ chunk_id, AAD =
header+FileEntry/ChunkEntry). Это позволяет расшифровать один чанк, не читая
остальные, но требует версионирования формата nonce (см. §7, тесты).

## 5. Инкрементальная распаковка

«Инкрементальность» здесь в двух смыслах:

1. **По файлам.** Распаковка чанка не требует распаковки соседних: zstd-кадры
   независимы, TOC лежит в начале и не сжат (или сжат отдельным чанком,
   который читается первым). Открытие игры стоит O(TOC + первый нужный файл),
   а не O(все ассеты).
2. **По времени.** Для больших файлов чанки распаковываются по требованию:
   `r2d_vfs_read` маленького диапазона (стриминг музыки, чтение заголовка PNG)
   не обязан тянуть весь файл. API потокового чтения — отдельная задача; в
   первой версии v3 достаточно «один файл = один или несколько чанков,
   распаковываем нужные».

Бюджет памяти: одновременно живут `plain`-кэш (ограничен, LRU) + один
распаковываемый чанк. `R2D_PAYLOAD_MAX_RAW` остаётся защитой от абсурдного
`raw_size`; дополнительно проверяется `compressed_size > 0` и
`offset + compressed_size <= body_size` **без переполнения** (как в текущей
проверке футера).

## 6. Обратная совместимость

* Читатель v3 обязан читать v1 и v2 — старые собранные игры не пересобираются.
* `magic` у v1/v2 и v3 разный (`R2DP` vs `R2D3`), поэтому выбор парсера —
  по магии+версии, без эвристик.
* `R2D_PAYLOAD_VERSION_MAX` поднимается до 3 **только** вместе с реализацией
  чтения v3; до этого `3` отвергается явным кодом `R2D_PAYLOAD_UNKNOWN_VERSION`.
* `R2D_PAYLOAD_VERSION_V3_PROPOSED` в `payload.h` — только именование для
  документа/тестов, не разрешение читать.
* Писатель: билдер (`src/build.c`) по умолчанию продолжает писать v2, пока
  v3 не пройдёт приёмку; переключение — флагом (`--payload-version=3`) и
  только после зелёных тестов и замера размера/времени старта.
* `r2d_payload_find`, `r2d_vfs_*`, владение буферами и коды ошибок не меняются.

## 7. План миграции

1. **Подготовка (без смены формата).** Вынести общий код чтения/поиска так,
   чтобы v1/v2 и v3 делили `r2d_payload_find` и проверки границ. Добавить
   seek-чтение футера вместо `SDL_LoadFile` — это улучшение можно включить
   раньше v3.
2. **Читатель v3 (только чтение).** HEADER/TOC/ChunkEntry, HASH-INDEX,
   exact+basename поиск, RAW и ZSTD-чанки, проверка всех `offset/size` и
   `crc32`. `R2D_PAYLOAD_VERSION_MAX` временно оставить 2, включить v3 за
   `#ifdef R2D_PAYLOAD_V3_READ` для тестов.
3. **Писатель v3 в билдере.** TOC → чанки → hash-index; детерминированный
   порядок (сортировка путей) ради воспроизводимого SHA256. По умолчанию OFF.
4. **Шифрование по чанкам.** Сначала без шифрования (raw/zstd) — проверить
   случайный доступ и память; затем AEAD на чанк; затем совместимость
   зашифрованных v1/v2.
5. **mmap.** POSIX `mmap`, Windows mapping, фолбэк `pread`; замер «время до
   первого кадра» на холодном кэше.
6. **Переключение по умолчанию.** Только после замеров: размер груза v3 vs v2
   (допустимо +2 %), время старта (цель — лучше v2), пиковая память (цель —
   не хуже v2 и не больше суммы используемых чанков).
7. **Удаление старого пути** — не раньше чем через релиз с v3 по умолчанию.

## 8. Тесты и критерии приёмки

Сейчас: `tests/payload/payload_test.c` (разбор, владение буфером, битые
записи) и новые `tests/payload/lookup_bench_test.c` (индекс путей: точный
поиск, суффиксный fallback, порядок первого совпадения, счётчики).

Для v3 добавить:

1. **Round-trip.** Билдер v3 → `r2d_payload_parse` → для каждого файла
   `r2d_payload_find` + побайтовое сравнение. Файлы: пустой, 1 байт, 64 КиБ,
   ровно на границе чанка, > 1 чанка, бинарные данные с NUL.
2. **Случайный доступ.** Чтение одного файла из груза на 10 000 файлов не
   должно распаковывать остальные: счётчик распакованных чанков/байт.
3. **Границы и порча.** Обрезанный HEADER/TOC, `offset+size` с переполнением,
   `raw_size=0`, `chunk_count=0`, битый zstd-чанк, неверный CRC32C — каждый
   случай даёт свой код ошибки, без OOB и без «тихо пустого груза».
4. **Утечки.** ASan/LSan на всех путях ошибок: индекс, TOC, чанки, кэш.
5. **Совместимость.** Один и тот же `r2d_payload_find` на v1, v2 и v3 даёт
   одинаковые ответы (включая суффиксный поиск и tie-breaking).
6. **Замеры.** Холодный старт (время до первого кадра), пиковый RSS,
   размер контейнера v2 vs v3, число syscall'ов чтения exe (цель — не читать
   весь exe).
7. **Безопасность.** Зашифрованный v3: подмена одного чанка не должна
   расшифровываться; AAD привязан к `file_id`/`chunk_id`.

Критерий готовности v3 — все пункты выше плюс отсутствие регрессий
`ctest -R "payload|audio"` и `tests/agent/payload_compression_test.py`.
